# 产品文档规范要求

**适用范围：** 以后所有项目的需求文档（PRD / 宣讲需求 / 开发测试需求）均按本规范编写。  
**来源：** 产品文档规范要求（B-PM-Veigar-综合，2025-06-02 修订）。  
**原则：** 文档必须能直接给开发、测试、宣讲使用；禁止只写概念、不写规则。

出任何新需求或改写现有需求时：先套本规范六段结构，再填该项目的业务内容。已锁定的产品原文不得因改结构而删掉。

---

## 一、需求背景与目标

必须写清四块：

| 块 | 写什么 |
|---|---|
| **背景** | 为什么做：现状问题、业务机会、依赖关系 |
| **路径 / 权限 / 联通** | 前台入口路径；后台入口路径；谁能进、谁不能进；和哪些系统/页面联通 |
| **目标** | 做成之后要达成什么（可验收，不要空话） |
| **业务要求** | 硬约束、范围边界、明确不做的事 |

---

## 二、详细功能说明

按功能逐条写，每一条都要覆盖：

1. **功能名称**
2. **功能说明**
3. **展示规则**（何时出现、对谁出现、文案/位置）
4. **交互逻辑**（用文字把点击/跳转/反馈写清楚，不要只丢截图）
5. **业务规则**（计算、门槛、次数、金额、状态流转）
6. **状态说明**（默认 / 进行中 / 成功 / 失败 / 禁用 / 空态）
7. **延伸**（关联功能、后续迭代、依赖）

功能很多时按模块分小节，但每一条仍要写全上述 7 点。

---

## 三、流程图 / 交互说明

用流程图（或等价步骤图）把用户路径画出来。至少覆盖：主路径、分支路径、回到哪一页。

文字交互已经写在「详细功能说明」里；本段负责让开发和测试一眼看懂走法。

---

## 四、异常场景

按下表模板列出，不要只写「接口失败就提示一下」。至少覆盖常见项；没有的标「不适用」并写原因。

| 异常场景 | 触发条件 | 用户感知 | 系统处理 | 是否可重试 | 备注 |
|---|---|---|---|---|---|
| 接口失败 / 超时 | | | | | |
| 空数据 / 无记录 | | | | | |
| 未登录 | | | | | |
| 无权限 | | | | | |
| 重复提交 | | | | | |
| 图片 / 资源加载失败 | | | | | |
| 页面加载失败 | | | | | |
| 第三方降级 | | | | | |

可按项目增补：余额不足、风控拦截、活动未开始/已结束、VIP 不够、网络断开后恢复等。

---

## 五、验收标准

必须可勾选、可打回。至少分这些类：

- **功能**：规则有没有按文档做对
- **页面**：入口、文案、展示对不对
- **交互**：点击、跳转、反馈对不对
- **数据**：计算、累计、展示口径对不对
- **异常**：第四节每一条是否按表处理
- **兼容**：PC / H5（及项目要求的浏览器/WebView）
- **性能**：首屏、接口超时、重复点击
- **埋点**：若本项目需要埋点，列出事件名和触发时机；不需要则写「本项目不要求」

---

## 六、风险预估

禁止只写「可能有问题」。每一条风险必须回答四问：

1. **是什么**
2. **影响是什么**（业务 / 资金 / 线上稳定性优先）
3. **出问题后怎么处理**
4. **有没有降级方案**

重点看：资金差错、重复发放、无法登录/无法进出、核心玩法中断、第三方不可用。

---

## 写作禁令

- 不要用改结构当借口删掉已锁定的产品原文、表格、验收清单、演示脚本。
- 不要把「详细功能说明」写成口号；没有展示规则、交互、业务规则、状态，就不算写完。
- 不要把风险写成担忧清单；没有处理和降级，就不算写完。
- 演示页 / 宣讲页可以短，但完整需求文档必须六段齐全。
